# GRAIN 1.2 — внедрение

Стандарт, который держится на памяти автора, умирает за месяц. GRAIN проверяется машинно на трёх уровнях, и все три читают один и тот же файл словарей.

```
grain.synx            словари как данные: глаголы, единицы, роли, пределы, уровни
   ├── ESLint-плагин  17 правил по AST для TypeScript — для подсветки в редакторе
   ├── grain          чекер: сам запускает эти правила по AST плюс имена файлов,
   │                  комментарии, Rust, SQL, Kotlin, Swift, SYNX — любой язык
   ├── baseline.synx  долг, принятый как данность: гейт валит только новое
   └── pre-commit     блокирует коммит по списку внедрения
```

Чекер не полагается на то, что в проекте настроен ESLint: он подгружает правила сам, поэтому одна команда проверяет и AST, и текст. ESLint в проекте нужен только для подсветки в редакторе; если его нет — правила всё равно исполняются в хуке и в CI.

## Установка

Чекер написан под [Bun](https://bun.sh) и ставится как обычная dev-зависимость:

```bash
bun add -d @aperturesyndicate/grain
```

После установки команда `grain` доступна через `bun grain` (или `bunx grain`). Чекер ищет корень проекта через `git rev-parse --show-toplevel`, а без git берёт текущий каталог; переопределить — переменной `GRAIN_ROOT`.

## Конфиг проекта

Пакет несёт полный словарь стандарта в своём `grain.synx`. Проект кладёт **свой** `grain.synx` в корень репозитория и переопределяет в нём только то, что отличается: ключ заменяется целиком, а не дополняется. Типичный конфиг:

```synx
# уровень, который проект держит
level 3

# где стандарт обязателен (пусто — весь репозиторий)
adopt src scripts

# чего чекер не открывает: сгенерированный код, сборка, зависимости
paths_ignored node_modules dist build src/db/migrations

# какие SYNX-файлы считаются конфигами (дисциплина имён спрашивается только с них)
synx_config app.synx

# единицы, которых нет в стандарте, но есть в домене проекта
units_domain Px Deg Hz Bpm Db Energy
```

Ключи `standard` и `version` принадлежат пакету и в проекте не переопределяются. Другой путь к конфигу — переменная `GRAIN_CONFIG`, к долгу — `GRAIN_BASELINE`.

## Уровни и бейдж

Проект объявляет уровень ключом `level` в своём `grain.synx`. Чекер проверяет ровно правила этого уровня — и не выдаст бейдж, если проект заявил больше, чем держит.

```bash
bun grain --all --level 1   # проверить только L1
bun grain --all --badge     # markdown-бейдж, если чисто
```

L3 отличается от L2 не правилами, а гарантией: проверка в CI, блокирующий pre-commit, `adopt` покрывает весь код, ни одного `GRAIN_SKIP` в истории. Это то, что нельзя проверить одним запуском линтера, но видно в репозитории.

## Команды

```bash
bun grain                    # staged-файлы (то же, что делает хук)
bun grain --all              # весь репозиторий по списку внедрения
bun grain --all --force      # весь репозиторий, игнорируя список
bun grain src/billing        # конкретный путь, без гейта
bun grain --json             # машинный вывод для CI
bun grain --all --baseline   # записать текущий долг
bun grain --audit            # заслужен ли объявленный уровень
bun grain --all --stat       # карта долга: кому до чистоты ближе всего
bun grain --explain <правило> # что проверяет правило
```

## Долг: baseline

Стандарт нельзя включить на живом репозитории «с завтрашнего дня»: код, написанный до него, нарушает его тысячами мест, и гейт, валящий всё подряд, снимается на второй день. Поэтому долг записан числами — `baseline.synx` в корне проекта, строка `<файл> <правило> <сколько>`:

```
src/billing/invoice.ts comment-form 8
```

Гейт пропускает ровно столько нарушений, сколько записано, и валит любое сверх. Значит: **новый код держит стандарт с первого дня, старый гасится по мере того, как до него доходят руки**. Номера строк в долге не хранятся намеренно — они едут при любой правке выше и превратили бы долг в источник ложных срабатываний.

Погасив часть, пересоберите долг — `bun grain --all --baseline`; чекер сам напоминает об этом, когда видит, что записанного больше, чем реального.

## Заслужен ли уровень

`grain --audit` проверяет не код, а обещание: для L3 обязаны существовать pre-commit, запускающий `grain` (в `.githooks`, `.husky` или каталоге из `core.hooksPath`), workflow в `.github/workflows` или `.gitlab-ci.yml`, запускающий проверку, и список внедрения, накрывающий весь проверяемый код. Объявить в `grain.synx` уровень, которого проект не держит, нельзя — аудит валится и называет причину.

## ESLint

```js
// eslint.config.js
import { grainConfig } from '@aperturesyndicate/grain'

export default [grainConfig]
```

Для кода, который мигрируется постепенно, — `grainMigrationConfig`: собственные правила GRAIN остаются ошибками, встроенные ограничения формы понижаются до предупреждений. `grainLevel1Config` — только правила L1.

| Правило | Что ловит |
|---|---|
| `grain/verb-lexicon` | Глагол не из словаря или запрещённый |
| `grain/find-get-contract` | `find*` без `null` в типе, `get*` с `null` |
| `grain/boolean-prefix` | Булево без `is/has/can/should/was/will/must` |
| `grain/unit-suffix` | Число без единицы измерения |
| `grain/no-vague-name` | Пустые слова, сокращения, самопохвала в именах |
| `grain/comment-form` | Комментарий без тега, `TODO`, разделители, эмодзи |
| `grain/no-emoji-log` | Эмодзи в логах |
| `grain/catch-must-act` | `catch`, который логирует и продолжает |
| `grain/no-redundant-temp` | Переменная на одну строку до `return` (автофикс) |
| `grain/no-default-export` | Экспорт по умолчанию |
| `grain/fail-code` | Код отказа не в форме `домен.предмет.причина` |
| `grain/file-role` | Роль в имени файла и kebab-case |
| `grain/no-dump-file` | Файлы и каталоги-свалки (`utils`, `helpers`, `common`) |
| `grain/dir-depth` | Иерархия каталогов глубже предела |
| `grain/boundary-effect` | Время, случайность, `process.env` внутри домена |
| `grain/inward-import` | Импорт наружу: домен узнал про I/O или про свою границу |
| `grain/explicit-parallel` | Независимые `await` по очереди вместо `Promise.all` |

Плюс встроенные правила ESLint, задающие форму: `max-depth`, `max-params`, `max-lines-per-function`, `max-lines`, `no-else-return`, `no-nested-ternary`, `no-lonely-if` — их пределы берутся из `grain.synx`, а не пишутся руками.

## Что машина проверить не может

Стандарт, который врёт про свои возможности, разваливается на первом ложном срабатывании. Поэтому честно:

| Правило | Состояние проверки |
|---|---|
| Мёртвый код | **Частично.** `no-dead-export` находит экспорт, который никто не упоминает в этом же репозитории, и только в режиме `--all`. Имя, вызываемое из другого репозитория или динамически, здесь неотличимо от мёртвого |
| Публичная поверхность по требованию | **Нет.** Требует знания всех потребителей пакета — проверяется на ревью |
| Комментарий отвечает «почему», а не «что» | **Частично.** Машина видит отсутствие тега, но не может отличить осмысленное «почему» от бессмысленного |
| Воронка `guard → acquire → derive → effect` | **Косвенно.** Через вложенность, длину и число аргументов |
| `find*` / `get*` без аннотации типа | **Нет.** Без объявленного типа возврата контракт не виден машине |
| Зеркало логики в оболочке | **Нет.** Что Kotlin повторяет правило ядра, видно только на ревью — это ошибка архитектуры, а не имени |
| Импорт наружу через пакет | **Нет.** `inward-import` видит относительные пути; `import { db } from '@scope/db'` в `*.pure.ts` пройдёт |
| Смысл кода отказа | **Форму — да, смысл — нет.** `fail-code` проверяет `домен.предмет.причина`; что домен назван верно, машина не знает |

## Pre-commit

```bash
#!/usr/bin/env bash
# .githooks/pre-commit
set -euo pipefail
cd "$(git rev-parse --show-toplevel)"
[ "${GRAIN_SKIP:-0}" = "1" ] && exit 0
bun grain
```

```bash
git config core.hooksPath .githooks   # один раз на клон
```

Хук проверяет **только проиндексированные файлы и только пути из списка внедрения**. Аварийный обход — `GRAIN_SKIP=1 git commit …`; обход остаётся в истории оболочки, а не в коде.

## CI

```yaml
# .github/workflows/grain.yml
name: grain
on: [push, pull_request]
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: oven-sh/setup-bun@v2
      - run: bun install
      - run: bun grain --all
      - run: bun grain --audit
```

## Где стандарта нет

Ключ `paths_ignored` перечисляет пути, на которых GRAIN неприменим: зависимости, сборка и **сгенерированный код**. Главный случай — миграции базы данных: применённую миграцию нельзя переписать, это застывшая история, а имена индексов и служебные комментарии в ней пишет генератор, а не автор. Без этого ключа каждая новая миграция валила бы коммит.

## Список внедрения

В `grain.synx` есть ключ `adopt` — пути, на которых GRAIN обязателен. Пустой ключ — весь репозиторий; с появлением долга так и должно быть:

```synx
adopt src
```

Правило простое: **новый модуль создаётся сразу по GRAIN**, и на него долг не записан — значит, он держит стандарт целиком с первого коммита. Существующий гасит свой долг, когда до него доходят руки, — модуль целиком, не по файлу: полумигрированный каталог хуже немигрированного, потому что перестаёт быть предсказуемым.

Порядок погашения долга модуля:

1. Переименовать файлы по ролям и разложить по доменам — это механическая правка, её видно в `git mv`.
2. Прогнать `bun grain <путь>`, починить имена, комментарии и контракты.
3. Пересобрать долг — `bun grain --all --baseline`; строки этого модуля должны исчезнуть из `baseline.synx`.
4. Закоммитить правки и обновлённый долг одним изменением: диффом видно, сколько именно погашено.

## Escape-хатч

Правило можно нарушить осознанно, но не молча:

```ts
// grain:allow unit-suffix — поле внешнего контракта Stripe, переименовать нельзя
```

Комментарий прикрывает названное правило на своей строке и на следующей. Причина обязательна — без неё чекер ругается на сам escape. Escape без причины и `GRAIN_SKIP` в CI приравниваются к нарушению.

## Изменение стандарта

`grain.synx` и документы в `docs/` меняются одним коммитом. Пополнение словаря — минорная версия; удаление глагола, роли или единицы — мажорная, потому что ломает существующий код.
